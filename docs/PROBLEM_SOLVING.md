# Problem Solving: TCP Stream Framing

## 관찰

2023년 멀티서비스 과제에는 텍스트 파일과 이미지 파일을 서버에서 클라이언트로 내려받는
기능과 실행 화면이 남아 있었습니다. 화면만 보면 두 파일 모두 생성되어 전송이 완료된
것처럼 보였습니다.

## 증거 비교

2026년 재검토에서 서버 원본과 클라이언트 수신 파일의 크기와 byte prefix를 비교했습니다.

| 대상 | 원본 대비 결과 |
|---|---|
| 텍스트 파일 | 원본 byte 전체가 동일한 prefix이고 뒤에 79byte 추가 |
| 이미지 파일 | 원본 byte 전체가 동일한 prefix이고 뒤에 79byte 추가 |

추가된 내용은 파일 종료를 나타내려던 `EOF` 문자열과 바로 다음 서비스 메뉴였습니다.
이는 우연한 파일 손상이 아니라 두 번의 논리 메시지가 하나의 TCP stream에서 합쳐진
결과임을 보여줍니다.

## 원인

TCP는 byte stream이며 다음을 보장하지 않습니다.

- 한 번의 `send()`가 상대의 한 번의 `recv()`와 대응
- 한 번의 `recv()`가 요청한 byte를 모두 반환
- 제어 메시지와 다음 메시지가 서로 다른 `recv()`로 분리

원본 구현은 buffer의 시작이 `EOF`인지 확인하고, 서버는 `EOF`를 보낸 직후 다음 메뉴를
전송했습니다. 두 데이터가 합쳐지면 클라이언트가 파일 데이터로 기록할 수 있습니다.

## 2026년 해결 방향

현재 공개 코드는 채팅 명령에 대해 다음 규칙을 적용합니다.

1. 각 명령과 채팅 메시지는 newline으로 끝납니다.
2. 클라이언트별 input buffer에 `recv()` 결과를 누적합니다.
3. newline이 있을 때만 한 메시지를 추출합니다.
4. 한 `recv()`에 여러 줄이 있으면 모두 순서대로 처리합니다.
5. 줄이 여러 `recv()`로 나뉘면 다음 byte가 올 때까지 보존합니다.
6. 송신은 `chat_send_all()`이 전체 byte가 전달될 때까지 반복합니다.

향후 binary 파일 전송을 다시 추가한다면 newline sentinel이 아니라 고정 크기 header에
payload length와 message type을 기록하고, 지정된 길이만 `recv_exact`로 읽어야 합니다.

## 독립 검증

- `/join 0\n`을 두 번의 send로 분할해 전송
- `/list\n/join 0\n`을 한 번에 전송
- NUL byte가 포함된 payload를 socket pair로 전송하고 길이·내용 비교
- 서버가 세 클라이언트의 방 입장·격리·브로드캐스트·퇴장을 처리하는지 확인
